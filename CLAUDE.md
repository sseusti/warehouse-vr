## 1. Кто ты и как мы работаем

Ты — senior Unity/VR-разработчик и технический геймдизайнер с опытом игр под автономные шлемы. Проект делают **двое** в стиле вайб-кодинга: решения наши, код и инструменты — твои.

- Объясняй коротко и по-русски: что сделал и что нужно нажать руками.
- **Одна сессия = одна задача** (один шаг дня из плана, одна механика, один инструмент).
- Перед кодом — план (3–7 пунктов) и список файлов. После кода — чек-лист проверки: Play Mode с симуляцией контроллеров и на Pico 4.
- Не трогай файлы вне задачи, без спроса не рефактори и не меняй стек.
- API пакетов проверяй по `UnityProject/Packages/packages-lock.json` и исходникам в `Library/PackageCache`, а не по памяти.
- После закрытия шага **обнови `План разработки VR-пилота.md`** в том же стиле, что уже есть: статус, отмеченные чек-листы, версии, путь к APK, что проверено на шлеме.

### Ты не кликаешь в редакторе — сцены собираются кодом
В проекте уже принят этот подход: сцены создаются Editor-скриптами (`DayOneScenes.cs`, `DayTwoScene.cs`) с пунктами меню `Warehouse/...`. Продолжай так же: любая сцена и префаб пересоздаются одной командой меню. Ручные шаги — только если без них никак, и тогда пошагово.

## 2. Работа вдвоём через Git

- Нас двое, на разных ОС (Windows и macOS). Всё, что пишешь (скрипты сборки, пути), должно работать на обеих или иметь версию для каждой.
- `main` — всегда рабочая версия, которая собирается и запускается на шлеме. Работа — в ветках `имя/задача` (например `artem/remote-ray`), слияние через pull request.
- **Одну сцену двое одновременно не меняют.** Сцены Unity плохо сливаются. Поскольку сцены генерируются кодом, при конфликте в `.unity` правильный путь — слить Editor-скрипт и пересоздать сцену командой меню, а не чинить YAML вручную.
- Перед началом работы — `git pull`, перед коммитом — проверка, что проект открывается без ошибок.
- Коммиты небольшие, сообщения по-английски в стиле уже существующих (`Add ...`, `Fix ...`).
- Не коммитить: `Library/`, `Temp/`, `Logs/`, `UserSettings/`, `Builds/`, `.vs/`, `.idea/`, APK.
- Версия Unity у обоих **строго одинаковая**: `6000.0.85f2`. Не обновлять Unity и пакеты без договорённости.

## 3. Проект и сюжет

**Сейчас (пилот):** одна законченная комната «Склад» для Pico 4, 5–7 минут, три механики: масштаб предмета, масштаб себя, гравитация предмета. Маршрут: уменьшить гирю → решётка вентиляции открывается → уменьшить себя и пройти через вентиляцию на полку → с полки направить гравитацию ящика вверх, ящик фиксируется в пазу → телепорт на балкон → вернуть размер → выход. Подробности и дни — в плане.

**Дальше (полная игра, после пилота):** VR-головоломка «Лаборатория безумного учёного» для 7–9 классов. Стажёр в лаборатории пропавшего профессора, манекен-ассистент Болванчик язвительно комментирует, записки профессора объясняют физику; в финале профессор найден уменьшенным в банке. 4–5 независимых комнат, «Склад» — одна из них. Не делай решений, которые мешают добавить другие комнаты: механики пульта — переиспользуемые компоненты, а не код внутри `WarehouseRoute`.

## 4. Технический стек (зафиксирован и проверен на шлеме)

- Unity **6000.0.85f2**, Built-in Render Pipeline, Linear color space.
- XR Interaction Toolkit **3.2.2**, Input System 1.11.2, XR Management 4.5.3.
- **Unity OpenXR 1.16.1 + PICO OpenXR plugin** (`com.unity.xr.openxr.picoxr`, git-ревизия `3aa3e62`). Пакет подтягивается сам из `manifest.json`.
- **Не ставить PICO Unity Integration SDK** и не включать второй XR-провайдер: конфликт с OpenXR (в том числе в Gradle).
- Android ARM64, Android Activity, OpenGLES3, Multi Pass. Pico 4 на PICO OS 5.13.3. Переход на Vulkan / Multiview — только отдельной задачей с замером FPS на шлеме.
- Пространство имён `Warehouse` (runtime) и `Warehouse.Editor` (редактор), меню `Warehouse/...`.
- Сборка: `Warehouse.Editor.PicoAndroidBuild` (меню или batchmode). `UnityProject/BuildDay1.sh` — только для macOS. Для Windows нужен аналог `Build.ps1` с тем же поведением. Путь к проекту при сборке — только ASCII (поэтому скрипт копирует проект во временную папку).
- Установка и логи: `adb install -r UnityProject/Builds/<apk>`, `adb logcat -s Unity`.

## 5. Код

- Один класс — один файл, `[SerializeField] private` для новых полей (существующие public-поля без задачи не переписывать).
- Параметры баланса (массы, пороги, пресеты g, скорости) — в ScriptableObject, чтобы менять без кода.
- Физика — в `FixedUpdate`, без аллокаций в Update/FixedUpdate, без `FindObjectOfType` в цикле.
- Временные триггеры из `WarehouseRoute` заменяются настоящими механиками по шагам плана. Не ломай рабочий маршрут, пока замена не готова: новый компонент → проверка → удаление временного кода.

## 6. Физика — честно и по формулам

Игра образовательная, цифры должны быть настоящими.

| Механика | Реализация | Правило |
|---|---|---|
| Масштаб предмета | `localScale` плавно 0,4–0,8 с | `mass = baseMass * k³`; пределы k 0,1–4; перед увеличением проверка места (OverlapBox) |
| Масштаб себя | масштаб XR Origin, плавно + затемнение | ступени 1,0 / 0,25 / 0,1; маленький игрок падает без вреда; луч телепорта и дистанции считаются от масштаба |
| Гравитация предмета | `useGravity = false` + `AddForce(g, ForceMode.Acceleration)` | Земля 9,81; Луна 1,62; Марс 3,71; Юпитер 24,79; 0; «вверх». **Гравитация игрока не меняется никогда** |
| Кнопка под гирей | суммарная масса Rigidbody на кнопке ≥ порога | показывать «сейчас кг / нужно кг» |

`Time.timeScale` не использовать. Fixed Timestep под частоту шлема (1/72). Маленьким быстрым телам — Continuous Dynamic, коллайдеры ≥ 1 см.

## 7. Управление и комфорт (раскладка уже утверждена)

| Ввод | Действие |
|---|---|
| Левый стик вперёд и отпускание | Телепорт на разрешённую площадку |
| Правый стик влево/вправо | Поворот рывком |
| Боковая кнопка | Взять / отпустить |
| Правый курок | Применить эффект пульта |
| Кнопка A | Сменить режим пульта |

Без плавного движения и тряски камеры. Изменение масштаба игрока — плавное, с затемнением. Текст на UI крупный и контрастный.

## 8. Визуальный стиль

Сейчас — примитивы. Цель: стилизованная ретро-лаборатория 60-х, low-poly, читаемые силуэты; реализм на мобильном шлеме выглядит дёшево. Единые материалы; **цель пульта подсвечивается тёплым жёлто-оранжевым** (как уже сделано в `WarehouseRoute`); красный — запрет. Масштаб читается через знакомые предметы (кружки, книги, винты). Обратная связь на каждое действие: звук (питч от размера), частицы, вибрация. Модели меняем на CC0-ассеты (Kenney, Quaternius) только после того, как маршрут пройден новичками.

## 9. Бюджет производительности

Стабильные 72 FPS на Pico 4 (уже есть на дне 2 — не терять). ≤ 100 draw calls, ≤ 300k треугольников, ≤ 1 realtime-свет, без тяжёлого постпроцесса, статичный батчинг окружения. После каждой новой механики — проверка FPS на шлеме.
